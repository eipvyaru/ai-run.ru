## 3. Тестовый пример EX01

Прочитать естественно, без произнесения названий знаков препинания:

> Меня зовут Марина. Мой учебный номер: плюс семь, ноль, ноль, ноль, один, два, три, четыре, пять, шесть, семь. Хочу обсудить обработку заявок. Созвон — третьего ноября две тысячи двадцать шестого года в пятнадцать тридцать по московскому времени.

Желательное оформление:

> Меня зовут Марина. Мой учебный номер: +7 000 123-45-67. Хочу обсудить обработку заявок. Созвон — 3 ноября 2026 года в 15:30 по московскому времени.

Проверяемые значения:

| Поле | Ожидается |
| --- | --- |
| Имя | Марина |
| Телефон | +70001234567 |
| Дата | 2026-11-03 |
| Время | 15:30, Europe/Moscow |
| Задача | Обсудить обработку заявок |

Допустимы иные пробелы, дефисы и пунктуация, а также числа словами, если они однозначно сохраняют все значения. Правильное оформление цифрами оценивается отдельно от сохранения смысла. Потеря хотя бы одной цифры номера или изменение даты/времени — критическая ошибка.

Первую запись назвать `EX01_S01_quiet.wav`. EX01 служит для настройки процедуры; не включать её в основной набор после подбора настроек на этом примере.

## 4. Подготовка одинакового входа

1. Записать каждую фразу один раз для каждого диктора. Предпочтителен WAV PCM16, mono, 16 кГц. Не обрезать начало и конец; оставить одинаковые короткие поля тишины.
2. Прослушать запись и вручную подтвердить эталон по тому, что действительно произнесено. При оговорке перезаписать файл либо заранее исправить эталон, не подгоняя его под распознаватель.
3. Сохранить длительность и SHA-256. Эти же файлы использовать для обоих вариантов. Ресэмплирование, усиление и другие преобразования делать одинаково и фиксировать.
4. В отдельном браузерном стенде подать файл как аудиотрек, если конкретный браузер действительно поддерживает этот способ. В текущем чате вызывается `start()` без аргумента; готовой подачи WAV там нет.
5. Если подача трека недоступна, использовать заранее настроенный виртуальный микрофон с тем же файлом. Прогон файла сначала через динамик, затем через обычный микрофон меняет сигнал и не подходит для строгого сравнения.
6. Проверить, что браузер действительно использует выбранный источник: контрольная запись с этого входа должна содержать тестовую фразу, а не комнатный микрофон. Если одинаковый вход обеспечить нельзя, пометить сравнение как эксплуатационное наблюдение, без заявления о точном преимуществе по WER.

Браузерный сервис может отправлять аудио внешнему поставщику; для него использовать только согласованные тестовые записи. Тест браузера измеряет текущую реализацию браузера, а не одну гарантированно неизменную модель.

## 5. Объём испытания

### Быстрая проверка

EX01, T03, T07 и N01: по одному прогону обоими вариантами. Проверить, что получаются текст, сохранённые цифры, дата/время и корректная обработка тишины. Такой объём не даёт основания утверждать преимущество по точности.

### Основной пилот

Три диктора с разными голосами. Каждый записывает T01–T16 в обычном и быстром темпе: две отдельные записи, без искусственного ускорения. Из записи обычного темпа дополнительно сделать шумовую версию с SNR 15 дБ. У обоих движков должны быть одинаковые шумовые файлы.

- 16 фраз × 3 диктора × 3 условия = **144 речевые записи**.
- Один общий файл для каждого N01–N03 и три записи N04 = **6 контрольных записей**.
- EX01 — отдельно для настройки.
- Всего основной набор: **150 файлов**. По три прогона на каждый движок = **900 результатов**.

Для SNR 15 дБ мощность шума рассчитывается относительно мощности речи на её активном участке: `noise_rms = speech_rms / 10^(15/20)`. Использовать фиксированный seed и один вид шума для основной серии; не допускать клиппинга. Новые типы шума проверять отдельной серией, не смешивая с основной.

Прогоны A/B чередовать и менять первый движок, чтобы не приписать движку изменение сети или нагрузки. Указать CPU/RAM, версии, потоки, загрузку системы и тип подключения. Модель загрузить один раз; первый вызов и загрузку измерить отдельно от трёх основных прогонов. Повторные прогоны одного файла не считать новыми независимыми примерами точности.

## 6. Что измеряем

| Показатель | Как оценивать |
| --- | --- |
| Точный телефон | Совпадение всех цифр после единой нормализации. Сохранить число удачных случаев и общее число. |
| Ошибки цифр | Количество замен, пропусков и вставок относительно эталонной последовательности; ведущие нули значимы. |
| Дата и время | Точное совпадение значений. Проверять смысл отдельно от формата записи. |
| Имя | Точное совпадение после приведения регистра и `ё/е`; фамилию не исправлять по предположению. |
| Текстовая точность | WER = `(замены + удаления + вставки) / число слов эталона`; считать на T01, T02, T10, T11, T12, где нет числовой нормализации. Отдельно показать примеры ошибок. |
| Пунктуация и регистр | Отдельная оценка T12 и EX01; не включать их ошибки в WER слов. |
| Задержка результата | От последнего речевого кадра исходного аудио до готового окончательного текста; минимум 0 мс. Показать медиану и p95. |
| Скорость модели | Отдельно время декодирования, загрузка и `RTF = decode_seconds / audio_seconds`. RTF не равен пользовательской задержке браузера или сервера. |
| Ресурсы | Память процесса и CPU; на VPS — также влияние параллельных запросов. |
| Надёжность | Доля завершённых запросов, обрезанные фразы, сетевые ошибки, зависания и текст на тишине/шуме. |

Для браузера окончательный текст собирать из завершённой попытки распознавания; промежуточные гипотезы не учитывать как отдельные ответы. Для каждой попытки сохранять итоговый текст или ошибку. Усечённая фраза — ошибка, а не повод незаметно перезапустить запись с середины.

## 7. Единые правила оценки

- Сохранять исходный результат каждого движка до любых исправлений.
- Для обычного текста: нижний регистр, `ё → е`, убрать пунктуацию и лишние пробелы. Для числовых фраз не использовать этот WER как основной критерий: «двадцать три» и «23» могут означать одно и то же.
- Для телефонов: одинаковые правила преобразования слов в цифры для обоих движков; убрать пробелы/скобки/дефисы; российский префикс `8` заменить на `+7` только у полного 11-значного номера. Не добавлять пропущенные цифры, не восстанавливать номер из эталона.
- Пока общего нормализатора нет, числовые значения размечать вручную по результату, желательно без указания движка. Не подключать LLM, исправляющую текст, к основному сравнению.
- Для относительных дат в наборе зафиксировано тестовое время **30.10.2026, 12:00, Europe/Moscow**. Поэтому в T09 «послезавтра» соответствует 01.11.2026. Это условие оценки, а не смена системных часов или обещание календарного слота.
- В T14 ASR должен сохранить произнесённое исправление. Выбор последнего времени — отдельная оценка смысла, не работа акустической модели.
- Незаполненное поле в CSV означает «не измерено», а не ноль. Неприменимые поля отмечать `NA`; ошибку движка не исключать из знаменателя надёжности.
- Три повтора нужны для устойчивости и времени. Точность основной серии считать по заранее выбранному первому прогону; остальные показывать отдельно. Не выбирать лучший результат из трёх.

## 8. Границы интерфейса и отдельный стенд

До согласия кнопка микрофона не должна начинать захват. После согласия пользователь может запустить и остановить ввод; текст остаётся редактируемым и не отправляется сам. Проверить запрет разрешения микрофона, повторный запуск, уход со страницы, паузу две секунды, длинную фразу и потерю сети. Потерянное окончание на паузе учитывать в результате текущих настроек браузера, не скрывать изменением `continuous` только для одного прогона.

ASR-стенд не должен вызывать LLM, создавать встречи или отправлять email. В текущем приложении не нажимать «Отправить» с тестовыми данными. Сначала сравниваются распознаватели, затем при отдельной реализации — взаимодействие с приложением.

После создания серверного стенда отдельно проверить VPS: один, два и четыре одновременных запроса, максимум длительности аудио, очередь/таймаут, загрузку модели один раз и освобождение ресурсов при отмене. Измерять задержку от окончания записи до появления текста, включая загрузку аудио по сети. Это будущая проверка: локальная модель пока не подключена к сайту и на VPS не установлена.

## 9. Предлагаемые критерии решения

Это ориентиры пилота, а не уже достигнутые показатели или гарантии сервиса:

- Не менее 98% точных телефонов и дат/времени; результат `punct` не хуже браузера на этих группах. Обязательно показывать числитель и знаменатель.
- Не менее 95% точных имён в простых условиях. Ошибки редких имён разобрать отдельно.
- Ни одного содержательного ответа на цифровой тишине; ошибки и текст на шуме учитывать отдельно.
- p95 пользовательской задержки не более 2 секунд после конца речи для фраз до 15 секунд на целевом стенде. Более длинные фразы — отдельная группа. Локальный decode сам по себе этот порог не подтверждает.
- Если ошибка хотя бы одной цифры или времени повторяется, исправление должно быть доступно пользователю до отправки; наличие кнопки редактирования не превращает ошибку ASR в успешное распознавание.

На небольшой выборке телефонных записей нельзя доказывать разницу в доли процента. При близких результатах расширить число дикторов и фраз; указать парные победы/поражения по одним файлам. Внедрять собственную модель ради контроля обработки можно и при сопоставимой точности, но такой мотив явно отделить от заявления «распознаёт точнее».

## 10. Итоговый отчёт

Заполнить CSV и подготовить короткое заключение: точные телефоны/даты/имена по группам, WER текстовых фраз, задержки, сбои и ресурсы. Приложить несколько пар ошибок на одних аудиофайлах. Итог выбрать из трёх вариантов: перейти на `punct`, оставить браузерный ввод или расширить испытание. Записи, шаблоны и прогнозы не выдавать за выполненный A/B-тест.
