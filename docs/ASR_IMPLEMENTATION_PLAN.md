### Когда можно остановиться до готовности

- Есть реальный риск потери production-данных или нарушения изоляции сервисов, который нельзя устранить в разрешённом объёме.
- Не хватает обязательного секрета/доступа, и нет безопасного локального способа продолжить зависимую часть.
- Несовместимость модели/runtime подтверждена воспроизводимой пробой, проверены доступные совместимые варианты, а исправление требует смены согласованной модели или архитектуры.

- Автоматическая проверка разрешений отклонила необходимое действие и безопасного разрешённого пути нет.

Перед остановкой выполнить все независимые работы, сохранить состояние, назвать точную причину, воспроизведение, предпринятые попытки и минимальное действие пользователя. ## 2. Согласованное поведение

- Варианты: browser и sherpa. Выбор администратора общий для приложения, хранится в SQLite.
- При первой установке этой функции активен sherpa. Последующие миграции и перезапуски не перезаписывают выбор администратора.
- Модель: sherpa-onnx-nemo-transducer-punct-giga-am-v3-russian-2025-12-16, revision a6039be7cee829a9044a69ac0ebaf1c191217c97. Использовать encoder.int8.onnx, decoder.onnx, joiner.onnx и tokens.txt.
- Локальный источник: C:\_Codex\_Models\sherpa-onnx-nemo-transducer-punct-giga-am-v3-russian-2025-12-16.
- Для посетителей production модель выполняется на VPS приложения, а не на компьютере разработчика.
- Запись прекращается повторным нажатием микрофона, кнопкой «Остановить», по тишине либо при достижении 60 секунд.
- При сбое Sherpa автоматически пробовать browser только на том же уже записанном аудио, максимум один раз.
- Если browser не может принять записанное аудио или тоже завершился ошибкой, показать ошибку и предложить ввод текста. Повторную диктовку автоматически не запускать, не предлагать её как обязательный шаг.
- При явно выбранном browser сохраняется обычный ввод с микрофона через Web Speech API. Его ошибка приводит к текстовому вводу; обратного fallback на Sherpa нет.
- Распознанный текст добавляется к исходному черновику один раз, остаётся редактируемым и никогда не отправляется в чат автоматически.
- До принятия согласия нельзя включать микрофон, записывать или отправлять аудио.
- Журнал: не более 1000 последних ошибок; не более 1024 байт UTF-8 служебных данных одного события. Старейшие удаляются автоматически.

### Рабочие значения, которые исполнитель выбирает без дополнительных вопросов

- Автоостановка Sherpa: 2 секунды тишины после обнаруженной речи; первые 10 секунд без речи завершают запись с сообщением «Речь не обнаружена».
- Минимум подтверждённой речи для окончания по тишине: 300 мс. Максимум всей записи: 60 секунд независимо от VAD.
- Начальная реализация определения активности: локальный Web Audio анализ уровня с оценкой фонового шума, сглаживанием и гистерезисом. Проверить тихую речь/шум; если качество не проходит приёмку, заменить на совместимый локальный VAD, сохранив интерфейс.
- Лимит загружаемого файла: 8 МиБ; после декодирования максимум 60 секунд, mono, 16 кГц. Длительность проверять по фактически декодированным данным, не доверять клиентскому полю.
- Один процесс модели, один одновременный decode, два CPU-потока; очередь максимум два ожидающих запроса.
- Внутренний бюджет обработки одного запроса: 45 секунд, внешний бюджет API: 50 секунд. Очередь входит в бюджет. Значения уточнять по замерам, документируя изменения.
- Аудио не хранить постоянно. В браузере Blob существует до окончания текущей попытки/fallback/отмены; на сервере временные данные удаляются при любом исходе.

## 4. Архитектура и контракты

Поток Sherpa: браузер MediaRecorder → POST /api/asr/transcribe → внутренний Python ASR → PCM16 mono 16 кГц → Sherpa → редактируемый текст.

Поток fallback: сохранённый Blob → браузерный audio MediaStreamTrack → SpeechRecognition.start(track), если этот способ действительно работает в браузере. При неподдерживаемом способе или ошибке → текстовый ввод.

Не включать браузерный распознаватель параллельно с Sherpa и не передавать аудио браузерной службе до отказа основного пути. Для fallback не использовать обычный start() без аудиотрека: он включил бы новый микрофон и нарушил согласованное правило.

### HTTP API приложения

- GET /api/asr/config: только публичные поля режима, ограничения длительности и настройки тишины; без внутренних URL, путей, секретов и подробностей инфраструктуры. Cache-Control: no-store.
- POST /api/asr/transcribe: multipart audio, идентификатор попытки и необходимые данные привязки к действующему согласию. Схему привязки выбрать после изучения текущей сессии; не считать произвольный sessionId доказательством согласия.
- Успех: { requestId, text, engine: "sherpa" }. Ошибка: { requestId, code, retryable }. UI переводит известный code в понятный текст.
- POST /api/asr/errors: ограниченный безопасный приём клиентских событий browser/fallback. Сервер проверяет enum-поля, размер, согласие/сессию и rate limit, отбрасывает неизвестные поля и свободный текст исключений.
- GET/PATCH /api/admin/asr: requireAdmin; чтение/сохранение режима и разрешённых параметров, состояние readiness модели. Отдельное сохранение не должно менять расписание/debug.
- GET /api/admin/asr/errors: requireAdmin; серверная пагинация, фильтры engine/code/stage, сортировка от новых к старым. Экспорт также только после авторизации.
- DELETE /api/admin/asr/errors: requireAdmin, проверка Origin/CSRF и подтверждение в UI; очищает только журнал ASR.

Все изменяющие маршруты: проверка Origin/CSRF, ограничения тела и частоты, валидация Zod, безопасные коды ошибок. Сначала проверить существующую защиту и переиспользовать её; не предполагать, что она уже есть во всех маршрутах.

### Внутренний Python API

- GET /health: жив ли процесс. GET /ready: модель загружена и готова.
- POST /transcribe: аудио и requestId от Node-сервера, ограниченный размер, внутренний токен из .env. Порт только на 127.0.0.1, не публиковать через Nginx.
- Ответ содержит только text/engine либо известный code. При переполнении очереди — 429/503 с кодом ASR_BUSY; при неготовой модели — ASR_NOT_READY.
- Python загружает модель один раз при старте; event loop не блокировать CPU-декодированием. Исполнитель выбирает простой совместимый HTTP runtime и фиксирует зависимости.
- Декодировать вход через FFmpeg без shell, передавать аргументы отдельным массивом; лимит времени, размера декодированного PCM и числа потоков. Нельзя формировать команду из пользовательского имени файла.
- При разрыве соединения/отмене не начинать ожидающий decode; для уже выполняемого decode ограничить время, убрать результат отменённого запроса и освободить временные ресурсы.

## 5. Схема данных и журнал

Новая миграция: INSERT OR IGNORE настройки asr_engine=sherpa и согласованных параметров; таблица asr_errors. Существующие consent records не изменять.

Предлагаемые столбцы журнала: id, created_at, request_id (случайный технический ID), engine, stage, code, duration_ms, http_status и ограниченный details_json из allowlist. Не хранить sessionId, IP, User-Agent, имя файла, аудио, транскрипт, ПДн, traceback, сырые сообщения браузера/FFmpeg и значения .env.

Проверять размер целого сериализованного события в UTF-8, включая служебные поля. Сначала урезать/отбрасывать необязательные details; не обрезать JSON посередине. Запись и удаление лишних строк выполнить одной транзакцией, устойчивой к параллельным запросам. Ограничить поля на уровне схемы/репозитория, не только UI.

Лимит 1000 событий ограничивает логический объём журнала; это не жёсткий предел размера файла SQLite/WAL. Не выполнять VACUUM после каждой записи. Проверить повторное использование страниц при длительной циклической записи и штатное поведение WAL. Сбой записи журнала не должен ломать ввод текста или раскрывать исходное исключение.

## 6. Клиентская машина состояний

Создать src/client/asr/ (или эквивалентный каталог): общие типы, контроллер, sherpa recorder/VAD, browser adapter, recorded-audio fallback. Компонент chat.tsx отвечает за UI и черновик, адаптеры — за распознавание и освобождение ресурсов.

Состояния: idle → requesting-microphone → recording → transcribing → completed; ветка ошибки Sherpa → fallback → completed/error; отдельная отмена → idle.

- При старте зафиксировать режим и исходный черновик; изменение настройки администратором применяется к следующей попытке.
- Каждой попытке назначить ID; устаревшие callback/ответы игнорировать. Блокировать параллельные старты и двойное добавление текста.
- При пользовательской отмене не запускать fallback и не регистрировать нормальную отмену как ошибку.
- Ошибка разрешения микрофона не запускает новый запрос микрофона через fallback: показать ошибку и текстовый ввод.
- После stop дождаться финального dataavailable MediaRecorder; отправить Blob один раз. Не обрезать последнее слово преждевременной остановкой треков.
- Сохранить Blob до результата Sherpa/fallback; затем освобождать треки, AudioContext, object URL, обработчики и буферы. То же при unmount/переходе страницы.
- Пустой/тишинный результат не считать успехом. Без аудио с речью не пытаться повторять распознавание бесконечно.
- Browser fallback: попробовать реально поддерживаемый путь start(track) с той же записью; наличия SpeechRecognition недостаточно для доказательства поддержки аргумента. Не использовать скрытый запуск с новым микрофоном.
- Browser fallback может окончиться неподдержкой/ошибкой сервиса. Тогда вернуть редактирование исходного черновика, показать «Не удалось распознать запись. Введите сообщение текстом» и записать безопасный код. Не требовать повторной диктовки.
- Кратко показывать «Запись», «Распознаём», «Пробуем браузерное распознавание». До возможного browser fallback посетителю должно быть понятно, что этот путь использует службу распознавания браузера. Юридические тексты самостоятельно не переписывать; проверить согласованность текущих уведомлений с новой обработкой.

Ранее пользователь показал успешный browser-прогон example.wav (11,29 с, время стенда 9,03 с). Это подтверждает техническую возможность в том браузере, но не точность и не полноту всей записи. Старый sample без независимого эталона не использовать для WER. Старые измерения GigaAM и полное время browser не объявлять равнозначными метриками.

## 9. План VPS и конфигурация

- Код: /var/www/ai-run.ru/asr/.
- Runtime: /var/lib/ai-run.ru/asr/venv/.
- Модель: /var/lib/ai-run.ru/asr/models/gigaam-v3-punct/.
- Временное аудио: /var/cache/ai-run.ru/asr/; ограниченные права и очистка устаревших файлов после аварии.
- Служба: deploy/systemd/ai-run-ru-asr.service, отдельный непривилегированный пользователь, автоматический перезапуск, NoNewPrivileges, ProtectSystem и строго необходимые writable paths.
- Внутренний порт выбрать после проверки реестра проектов и занятости VPS; значение записать в документацию и конфигурацию. Не занимать 8787, PLAYWRIGHT_PORT=8786 и порты других проектов.
- Пример env-контракта: ASR_SERVICE_URL, ASR_SERVICE_TOKEN, ASR_MODEL_DIR, ASR_TEMP_DIR, ASR_MAX_AUDIO_SECONDS, ASR_MAX_UPLOAD_BYTES, ASR_REQUEST_TIMEOUT_MS, ASR_NUM_THREADS. Режим пользователя хранить в SQLite, а не дублировать редактируемым флагом env.

Перед будущим deployment: проверить CPU/RAM/диск и базовую нагрузку VPS, точную версию Python, wheel для архитектуры и FFmpeg. Первые ресурсные пределы systemd выбрать после замера реального пикового RSS; не угадывать лимит памяти ниже потребления модели. Отказ очереди должен быть управляемым, OOM недопустим.

Модель передавать отдельно от Git, проверять каждый файл по manifest.json с revision и SHA-256. Не скачивать latest без фиксации. Для обновления сначала подготовить новую директорию, проверить decode, затем переключить ASR_MODEL_DIR и перезапустить только ASR-службу.

Nginx: проверить client_max_body_size и proxy timeout только для ai-run.ru и ASR-маршрута. Не менять другие сайты. Внутренний Python-порт не проксировать публично. Размер multipart должен учитывать накладные расходы сверх 8 МиБ аудио, но приложение строго ограничивает сам файл. Настройка serverActions.bodySizeLimit не заменяет лимиты Route Handler/Nginx.

Проверка readiness: браузерный режим не зависит от готовности Python. При выборе Sherpa админка показывает деградацию при отказе модели, но существующий чат/календарь/текстовый ввод остаются доступны. Не превращать отказ ASR в общую недоступность сайта без явного обоснования.

Будущий deployment: verify:release → push разрешённого commit → read-only аудит VPS → сохранить PREVIOUS_COMMIT и конфигурацию → checkpoint перед потенциально опасной миграцией → установить runtime/модель и проверить их → checkout точного commit → npm ci/checks/build → штатно применить новые миграции → запустить ASR и проверить ready → перезапустить веб-сервис → публичные проверки и browser smoke. Существующие .env, SQLite и prompt сохранять.

Rollback: переключить режим на browser, при необходимости вернуть PREVIOUS_COMMIT и конфигурацию службы, пересобрать и перезапустить. Не откатывать SQLite копированием и не удалять evidence согласий. Новая миграция должна быть совместима с предыдущим веб-релизом (добавочные таблицы/settings).

## 10. Обязательная матрица проверок

1. Миграция пустой и существующей тестовой БД; default sherpa; повтор миграции сохраняет browser, выбранный администратором.
2. До согласия нет capture/upload/распознавания; подделанный sessionId не даёт доступ.
3. Sherpa: настоящий WAV, WebM/Opus, поддерживаемый MP4/AAC, неверный контейнер/MIME, повреждённый файл, пустой файл, >8 МиБ, >60 с, многоканальный/иной sample rate.
4. Запись: ручной stop, 60 с, тишина до речи, тишина после речи, тихая речь, фон, двойной click, отмена, уход со страницы, запрос разрешения отклонён.
5. Сохранение черновика и ровно одно добавление транскрипта; поздние ответы старой попытки не меняют поле; отправки в чат нет.
6. Отказ Sherpa/timeout/queue full → один fallback на сохранённое аудио. Browser неподдерживаем/отказал → текстовый ввод. Повторного микрофона и повторной диктовки нет.
7. Browser выбран явно: штатный микрофонный путь, запись ошибки, текстовый ввод при отказе; скрытого Sherpa-запроса нет.
8. Лог: 1001+ ошибок, многобайтовые символы, oversized детали, конкурентная запись/очистка, фильтры, страницы, экспорт. Нет аудио/текста/ПДн/secrets, каждое событие <=1024 байт, количество <=1000 после транзакции.
9. Защита: анонимные admin API, неверный Origin/CSRF, превышение частоты, поддельные engine/code, служебный Python без токена, path traversal через имя файла.
10. Python: cold start, три тёплых decode, параллельно 1/2/4 запроса, bounded queue, отмена, остановка/рестарт и уборка временных файлов. Замерить RSS/CPU/время, не выдавать оценку Windows за VPS.
11. Desktop/mobile UI: компактная админка, доступность клавиатурой, индикатор записи, понятный режим/fallback, отсутствие горизонтального scroll.
12. Регрессия расписания, согласий, legal registry, логов диалогов и базовых тестов; LLM/CalDAV/SMTP только mock, без реальных платных/production действий.

Автоматические проверки писать для содержательных границ: безопасность, лимиты, состояние, fallback, очистка и кольцевой журнал. Не создавать тесты, которые просто повторяют строки реализации. Python-проверки включить в release workflow через воспроизводимое окружение; обычная проверка не скачивает веса и не требует production-сервиса. Настоящий model smoke — отдельный локальный шаг с зафиксированным результатом.

## 11. Рабочий цикл и решение сбоев

После каждого этапа: diff review → подходящие проверки → исправления → локальный commit. Не использовать --no-verify. Hook может создавать commit и затем сообщать о провале post-commit проверки: проверять SHA и статус отдельно, чинить причину, не объявлять release готовым до успешного verify:release.

При ошибке определить, относится ли она к коду, env, runtime, браузерной возможности или инструменту автоматизации. Воспроизвести минимально, проверить гипотезу, исправить и повторить затронутые проверки. Не перезапускать полный набор без причины после каждого мелкого шага, но финальный verify:release обязателен.

Если Windows UI-инструмент не может подтвердить URL, не повторять тот же вызов бесконечно и не обходить его запрет. Использовать разрешённый browser API с точным localhost URL либо отдельный управляемый тестовый браузер/стенд. Отсутствие SpeechRecognition в Codex IAB учитывать как неподдерживаемую платформу. Если обычный браузер недоступен автоматизации, продолжать API/model/автоматизированные UI проверки; явно отметить недоказанную часть приёмки, а не подменять её успехом.

## 13. Критерии готовности к развёртыванию

- Выполнены согласованные требования раздела 2; новая установка выбирает Sherpa.
- Настоящая модель локально распознаёт запись браузера; два режима и админское переключение работают.
- Автоматический fallback либо обрабатывает тот же Blob, либо корректно заканчивается текстовым вводом без повторной диктовки.
- Ограничения аудио, очередь, авторизация, очистка и кольцевой журнал проверены содержательными тестами.
- Администратор видит режим, readiness, ошибки и может просмотреть/экспортировать/очистить журнал.
- Зависимости закреплены, файл модели проверяется по SHA, есть systemd unit, env-пример, инструкции установки/обновления/rollback и перечень VPS-предпроверок.
- verify:release завершился кодом 0, настоящие локальные smoke-проверки записаны в ASR_RELEASE_READINESS.md. Каждый непроверенный браузер/формат помечен явно.
- Итоговый release-коммит известен, рабочее дерево чистое с учётом правил генерируемых Next-файлов, секретов и аудио в Git нет.
- В финальном сообщении: SHA, что реализовано, результаты проверок, реальные ограничения, что нужно выполнить на VPS. Не заявлять production-готовность по нагрузке VPS до фактических VPS-замеров; отделить готовность пакета к развёртыванию от проверенной работы на сервере.
